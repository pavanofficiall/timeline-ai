====================================
1) Executive Summary
====================================
Goal: Deliver a dependable Case Workspace that transforms uploaded legal documents (PDF/images) into a unified, chronologically ordered, deduplicated, and explainable master timeline per case. Priorities: correctness, latency, observability, privacy, and predictable costs.

Near‑term outcomes (2–4 weeks):
- Upload responds quickly (enqueue background processing); OCR+LLM extraction completes ≤ 2 min p95.
- ≥ 90% of clear PDFs produce ≥ 1 structured event; JSON parse failures ≤ 5% with repair.
- Case timeline UX supports source links, confidence badges, filters, and consistent mobile/desktop layouts.

KPIs:
- Extraction success rate (events > 0) on clear PDFs ≥ 90%.
- Case timeline API p95 < 200 ms for ≤ 100 events.
- Error budget for upload failures < 1%.

====================================
2) Product Scope & User Journeys
====================================
Primary Personas:
- Lawyer/Paralegal: Upload documents, get a consolidated timeline, identify missing items, plan actions.
- Admin/PM: Monitor extraction health, costs, and model quality; manage configs/limits.

Core Journeys:
1) Create a case → Upload 1–3 PDFs → System extracts events/parties/payments/missing → Master timeline updates → User opens source file from timeline.
2) Add more documents later → Timeline merges new events, deduplicates, flags conflicts.
3) Review missing documents and payments summaries; export timeline; annotate if needed (later).

3) System Architecture Overview
====================================
Frontend (Next.js 16 App Router, shadcn UI):
- /cases: list/create cases (recent first).
- /cases/[id]: Case Workspace (multi‑upload; docs list; merged timeline with confidence, type tags, parties, source links). Only top navbar (no sidebar) per design.
- /documents, /timeline/[id]: legacy debugging surfaces (kept during iteration).
- /admin/logs: dev‑only logs viewer.

APIs:
- Cases: GET/POST /api/cases; GET /api/cases/:id; POST /api/cases/:id/upload; GET /api/cases/:id/docs; GET /api/cases/:id/timeline.
- Documents: GET /api/documents/[id]/timeline; GET /api/documents/[id]/file (signed URL or direct).
- Debug: /api/debug/storage, /api/debug/db.

Backend services:
- OCR pipeline (backend/lib/ocr.ts): text‑layer extraction first; Gemini Vision preferred (2.5 → 2.0 → 1.5); OCR.Space fallback for scans.
- Preprocessing (backend/services/fileProcessor.ts): detect → extract → clean text; write OCR preview logs.
- Extraction (backend/services/aiExtractor.ts): prompt → Gemini → JSON parse (repair planned) → normalize; heuristic fallback for vertical tables and “Events Log”.
- DB/Storage (Supabase): private ‘documents’ bucket; service‑role server‑side client; helpers for robust queries.

Data flow (happy path):
1) Upload → store file (private bucket) → insert document row (status=pending).
2) Background job (planned) or synchronous MVP: OCR + extraction → insert case_events/parties/payments/missing → update document status=processed.
3) Timeline read: GET /api/cases/:id/timeline merges & dedupes by (date,title,description), infers type (Payment/Contract/Message/Court/Missing/Update) for UI when not yet persisted.

5) Extraction Pipeline (Deep Dive)
====================================
Text acquisition:
- Prefer PDF text‑layer extraction (cheap/fast). If absent/low coverage → per‑page OCR.
- Detect language; enable Unicode normalization; for Hindi pages, route prompts/heuristics accordingly.

Prompting (Gemini 2.5 flash preferred):
- Strict JSON only (no prose), with schema keys: events[], parties[], payments[], missing_documents[].
- Include examples with ISO dates (YYYY‑MM‑DD), numeric amounts, and short titles.

JSON parsing & repair (planned):
- Strip Markdown fences, fix trailing commas, balance brackets/braces.
- Validate with zod; coerce dates and numbers; default confidence when absent.

Heuristic fallback:
- Parse “vertical tables” by headings (Missing Documents / Identified Parties / Payments) and the “Events Log” section.
- Normalize currency symbols (₹, Rs., INR) and artifacts (■) while preserving original strings where needed.

Confidence:
- If model returns confidence, store as confidence_score (0..1). When missing, set by heuristic defaults (payments 0.6, missing 0.4, events log 0.5) until calibrated.

====================================
6) Event Typing, Deduplication, Conflicts
====================================
Event typing (current UI inference → planned persistence):
- Inference rules: keyword sets for Payment, Contract, Message, Court, Missing; default Update.
- Persist event_type once schema migrates to enum for filterable UI and analytics.

Deduplication (master timeline):
- Key = lower(normalize(title)) + lower(normalize(description)) + date.
- Keep first occurrence; store provenance (document_id) list in future (for audit and “occurs in multiple docs”).

Conflict detection:
- Same normalized (title, description) but different dates/amounts across docs.
- Flag in response summary: { added, duplicatesIgnored, conflictsFlagged } and show UI badge.

====================================
7) Cost, Latency, and Scale
====================================
Levers:
- Reduce LLM tokens by chunking (per section/page) and summarizing ahead of extraction when text is long.
- Cache by text hash to avoid re‑extracting identical content across uploads.
- OCR only when text layer absent; per‑page OCR avoids full‑doc cost.

Targets:
- Upload API p95 < 3s (enqueue); OCR+extract p95 ≤ 120s; timeline read p95 < 200ms.

Storage & egress:
- Private bucket, short‑TTL signed URLs; avoid public links. Consider pre‑signed caching for preview.

====================================
8) Security, Privacy, and Compliance
====================================
Secrets & access:
- Server‑only service role key; never expose in client bundles. Optional anon key for public read surfaces only with RLS.

RLS (phase 2):
- Enable RLS on cases/documents/events with case_members table (user_id, case_id, role). Policies: users see only cases they belong to.

PII controls:
- Minimize logging of content; redact PII in logs; configurable retention of OCR and extraction artifacts.

Audit & provenance:
- Keep extraction logs; store model id/version; optionally store page anchors/spans.

RLS policies & case_members schema (detailed):
- case_members(
  id uuid pk default gen_random_uuid(),
  user_id uuid not null,
  case_id uuid not null references public.cases(id) on delete cascade,
  role text not null check (role in ('owner','editor','viewer')),
  created_at timestamptz not null default now()
)
- Indexes: unique (user_id, case_id), index on (case_id)
- Enable RLS on cases, documents, case_events, case_parties, case_payments, missing_documents
- Policies (example):
  - cases: select where exists (select 1 from case_members cm where cm.user_id = (current_setting('request.jwt.claims', true)::json->>'sub') and cm.case_id = cases.id)
  - documents: select where case_id in (select case_id from case_members where user_id = (current_setting('request.jwt.claims', true)::json->>'sub'))
  - events/parties/payments/missing: select where document_id in (select id from documents where case_id in (select case_id from case_members where user_id = (current_setting('request.jwt.claims', true)::json->>'sub')))
- Writes: restrict to role in ('owner','editor'); viewers read-only. Consider separate upload scope.

17) Cost Modeling — Rough Monthly Estimates (OCR/LLM/Storage/Egress)
====================================
Important: These are illustrative estimates to guide planning. Replace rates with your vendor pricing and re‑compute using the formulas below. LLM Vision pricing varies significantly across providers and regions; treat this as directional only.

Baseline assumptions (override as needed):
- Documents per month (D): small=500, medium=2,500, large=10,000
- Avg pages per document (P): 10
- Pages requiring OCR (%OCR): 40% (text layer present on the rest)
- PDF size per page (MBpp): 0.30 MB (scanned PDFs can be 0.2–0.5 MB/page)
- Views per month: 25% of uploaded documents opened once (signed URL)
- Avg egress per view: 2 MB
- LLM extraction tokens per doc: input=3,500 tokens, output=600 tokens (after cleaning/chunking)

Example unit rates (replace with your vendor rates):
- OCR_RATE_PER_1K_PAGES = $1.50 per 1,000 pages (commodity OCR API example)
- LLM_IN_RATE_PER_1K = $0.20 per 1,000 input tokens (text model)
- LLM_OUT_RATE_PER_1K = $0.60 per 1,000 output tokens (text model)
- STORAGE_PER_GB_MONTH = $0.02 per GB‑month
- EGRESS_PER_GB = $0.09 per GB

Formulas:
- Pages/month = D × P
- OCR pages/month = Pages × %OCR
- OCR cost = (OCR pages / 1,000) × OCR_RATE_PER_1K_PAGES
- LLM input tokens/month = D × 3,500; cost = (tokens/1,000) × LLM_IN_RATE_PER_1K
- LLM output tokens/month = D × 600; cost = (tokens/1,000) × LLM_OUT_RATE_PER_1K
- Storage added/month (GB) = D × P × MBpp ÷ 1,024
- Storage cost/month = Storage added × STORAGE_PER_GB_MONTH
- Egress/month (GB) = (D × 25% × 2 MB) ÷ 1,024
- Egress cost = Egress × EGRESS_PER_GB
- Total ≈ OCR + LLM(in+out) + Storage + Egress

Scenario A — Small team
- D=500; P=10 → Pages=5,000; OCR pages=2,000
- OCR ≈ (2,000/1,000)×1.50 = $3.00
- LLM in ≈ (500×3,500 / 1,000)×0.20 = 1,750×0.20 = $350.00
- LLM out ≈ (500×600 / 1,000)×0.60 = 300×0.60 = $180.00
- Storage ≈ (500×10×0.30 / 1,024)×0.02 ≈ 1.46 GB×0.02 ≈ $0.03
- Egress ≈ (500×0.25×2 / 1,024)×0.09 ≈ 0.24 GB×0.09 ≈ $0.02
- Total ≈ $533.05/month (LLM dominates)

Scenario B — Growing firm
- D=2,500; Pages=25,000; OCR pages=10,000
- OCR ≈ (10,000/1,000)×1.50 = $15.00
- LLM in ≈ (2,500×3,500 / 1,000)×0.20 = 8,750×0.20 = $1,750.00
- LLM out ≈ (2,500×600 / 1,000)×0.60 = 1,500×0.60 = $900.00
- Storage ≈ (2,500×10×0.30/1,024)×0.02 ≈ 7.32 GB×0.02 ≈ $0.15
- Egress ≈ (2,500×0.25×2/1,024)×0.09 ≈ 1.22 GB×0.09 ≈ $0.11
- Total ≈ $2,665.26/month

Scenario C — Mid‑size firm
- D=10,000; Pages=100,000; OCR pages=40,000
- OCR ≈ (40,000/1,000)×1.50 = $60.00
- LLM in ≈ (10,000×3,500 / 1,000)×0.20 = 35,000×0.20 = $7,000.00
- LLM out ≈ (10,000×600 / 1,000)×0.60 = 6,000×0.60 = $3,600.00
- Storage ≈ (10,000×10×0.30/1,024)×0.02 ≈ 29.30 GB×0.02 ≈ $0.59
- Egress ≈ (10,000×0.25×2/1,024)×0.09 ≈ 4.88 GB×0.09 ≈ $0.44
- Total ≈ $10,661.03/month

Sensitivity & knobs:
- If using LLM Vision for OCR (an LLM sees page images), treat OCR as LLM input tokens per page; costs can 10×–50× OCR API rates. Prefer text‑layer extraction and commodity OCR fallback.
- Reduce tokens by chunking (per section/page) and reusing results via text‑hash cache. Skip re‑extraction when documents re‑upload unchanged.
- Lower egress by rendering in‑app previews (range requests) and caching signed URLs briefly.
- Storage growth scales with retention; if keeping 24 months, multiply storage estimates accordingly.

Budget guardrails:
- Set monthly caps for LLM/OCR; fallback to heuristics when approaching limits.
- Alert on token surge (per case, per user) and queue depth spikes.

18) Queue/Worker Design — Retry, Backoff, Idempotency, Concurrency
====================================
Goals & guarantees:
- At-least-once processing with idempotent handlers (safe re-runs)
- No lost jobs; bounded retries with exponential backoff + jitter
- Dead-letter path for non-retriable or exhausted jobs
- Visibility into states, errors, and latencies

Jobs table (proposed):
- jobs(
  id uuid pk default gen_random_uuid(),
  type text not null check (type in ('extract_document')),
  case_id uuid null references public.cases(id) on delete set null,
  document_id uuid not null references public.documents(id) on delete cascade,
  payload jsonb null,
  status text not null default 'queued' check (status in ('queued','processing','done','error','dead')),
  attempts int not null default 0,
  max_attempts int not null default 6,
  last_error text null,
  idempotency_key text null,
  next_run_at timestamptz not null default now(),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
)
- Indexes:
  - jobs_status_next_idx on (status, next_run_at)
  - jobs_doc_idx on (document_id)
  - unique (idempotency_key) nulls not distinct (optional)

Producer (upload path):
- Compute idempotency_key (e.g., sha256(case_id + storage_path + file_size) or content hash if feasible)
- Insert job with idempotency_key; ON CONFLICT(idempotency_key) DO NOTHING to avoid duplicates; record job_id on documents row for traceability

Claiming jobs (worker):
- SELECT id FROM jobs WHERE status='queued' AND next_run_at <= now()
  ORDER BY next_run_at ASC LIMIT N FOR UPDATE SKIP LOCKED;
- Immediately UPDATE status='processing', attempts=attempts+1, updated_at=now()
- Process in-memory with try/finally; on graceful shutdown, stop claiming new jobs

Processing steps (idempotent by design):
1) Read document row; if status='processed' and a stable marker matches (e.g., content_hash), short-circuit to done
2) Fetch storage object by path; compute content_hash (sha256) for idempotency/audit
3) OCR/Text: cache by content_hash+engine to avoid re-OCR; persist ocr preview
4) LLM extraction: cache by text hash; validate/repair JSON; normalize
5) DB writes:
   - Prefer DB-level dedupe where possible. Options:
     a) Application dedupe key (case_id, date, lower(title), lower(description)) as we do, or
     b) Add generated columns normalized_title/description (lower(trim(...))) and create a UNIQUE INDEX on (case_id, date, normalized_title, normalized_description); then INSERT ... ON CONFLICT DO NOTHING
   - Insert parties/payments/missing with natural keys when possible (e.g., document_id + normalized fields) to avoid duplicates
6) Update documents.status='processed', store processing_version = content_hash (new column) and last_processed_at

Retry & backoff policy:
- Backoff schedule with jitter (attempt N → delay):
  1: 1m, 2: 5m, 3: 15m, 4: 1h, 5: 6h, 6: 24h
- next_run_at = now() + delay + rand(0..delay*0.1)
- Classify errors:
  - Non-retriable (4xx invalid file, schema mismatch that can’t be fixed programmatically) → status='dead'
  - Retriable (429/5xx, timeouts, quota) → backoff

Concurrency & rate limits:
- MAX_CONCURRENCY configurable (e.g., 2–8)
- Provider budgets: token bucket per provider (e.g., Gemini QPS/RPM); if bucket empty, reschedule with short delay
- Use Promise pool in worker route; avoid stampedes (claim small batches)

Timeouts & cancellation:
- Per-step timeouts (OCR, LLM) with abort; on timeout, treat as retriable
- Ensure process aborts cleanly on server shutdown; in-flight jobs either complete or will be retried by next_run_at

Idempotency details:
- Storage path naming: prefix with timestamp but rely on content_hash for canonical identity
- Persist content_hash on documents; skip reprocess if unchanged
- Upserts/ON CONFLICT DO NOTHING on dedupe keys for events/parties/payments/missing

Dead-letter & requeue:
- status='dead' rows visible in admin; include last_error and attempts
- Admin action: move to queued with attempts=0 (if underlying issue fixed)

Observability:
- Metrics: jobs queued/processing/done/dead; avg attempts; backlog age; step latencies
- Logs: job_id, document_id, case_id on every log line; summarize on completion (added, duplicatesIgnored, conflictsFlagged)

Operational playbook:
- Quota exceeded → widen backoff base, reduce concurrency, or switch to fallback OCR/model
- Reprocessing a case after prompt update → enqueue jobs for all case documents with new processing_version target; idempotent writes will avoid duplicates
